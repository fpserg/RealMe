# Architectural Change Request — Replace Horizon with Calendar Projection

## Purpose

Refine the temporal presentation layer without changing the underlying architecture.

The Temporal Engine is working correctly and should remain a core architectural component.

The proposed change concerns only how temporal information is projected to the Warden.

---

# Architectural Principle

RealMe should innovate in reasoning, not in basic human interaction patterns.

The Warden already possesses decades of intuition for navigating time through calendars.

The application should leverage that intuition rather than replacing it with a novel temporal interface.

The intelligence should exist beneath the interface, not inside the interface itself.

---

# Current Issue

The current **Horizon** view exposes the internal reasoning model directly.

While architecturally correct, it creates unnecessary cognitive load because it requires the Warden to learn a new mental model for something already well understood.

The Portal is also becoming overloaded.

Instead of serving as a calm orientation point, it increasingly resembles an operational dashboard.

---

# Required Change

Keep the existing:

- Temporal Engine;
- planning rules;
- recurrence engine;
- business-day calculations;
- activation logic;
- preparation windows.

Do **not** remove or simplify these systems.

Only replace the primary UI projection.

---

# Portal

The Portal should answer one question:

> Where is my World right now?

It should remain intentionally calm.

Suggested contents:

- current operational state;
- Realm summary;
- today's most important commitments;
- one or two approaching thresholds;
- recent meaningful World changes.

Do **not** display a complete forward schedule on the Portal.

The Portal is an orientation surface, not a planning surface.

---

# Replace "Horizon" with "Calendar"

The current Horizon screen should evolve into a familiar calendar projection.

Suggested views:

- Week
- Month
- Agenda (optional)

The calendar is **not** the source of truth.

It is a derived projection of the World Model.

---

# Calendar Semantics

Unlike a traditional productivity application, the calendar should display derived temporal knowledge.

Examples include:

- scheduled meetings;
- recurring commitments;
- deadlines;
- birthdays;
- preparation tasks generated by planning rules;
- dependency milestones.

Example:

15 Aug — VK Results

↓

Planning Rule

↓

13 Aug — Prepare VK Preview

The preparation task should appear automatically.

The user should never create it manually.

---

# Preserve WBT as the Core

The hierarchy should become:

Portal

↓

Today (WBT)

↓

Calendar

↓

World Map

↓

Dialogue

WBT remains the primary operational surface.

The Calendar provides temporal orientation.

The World Model remains the source of truth.

---

# WBT vs Calendar

The distinction must remain explicit.

## WBT answers:

> What belongs to today?

## Calendar answers:

> When do known things occur?

A commitment should appear in WBT because it is currently actionable.

A commitment should appear in Calendar because it possesses meaningful temporal structure.

These are different projections of the same World.

---

# Calendar Population Rules

Only display items that possess explicit temporal structure.

Examples:

- scheduled events;
- recurring commitments;
- deadlines;
- birthdays;
- planning-rule activations;
- dependency milestones.

Do **not** permanently display vague ongoing commitments such as:

- Continue brokerage framework.
- Improve RealMe.

Those belong to the World Model and appear in WBT when activated.

---

# Rename Horizon

"Horizon" should remain an internal architectural concept.

It should no longer be the primary user-facing navigation label.

Internally:

Temporal Engine
↓

Horizon Projection

↓

Calendar View

The implementation keeps Horizon.

The Warden sees Calendar.

---

# Portal Preview

Instead of embedding the Horizon view, display only a compact "Approaching" section.

Example:

Approaching

• Thu — Positive Technologies IR Call

• In 12 days — VK Results

• In 18 days — Strategy Report Planning Threshold

Selecting any item opens the Calendar at the corresponding date.

---

# Architectural Principle

The underlying reasoning remains uniquely RealMe.

The presentation becomes immediately understandable.

The goal is not to imitate productivity applications.

The goal is to project RealMe's superior temporal reasoning through interaction patterns the Warden already understands.

The architecture remains:

World Model

↓

Temporal Engine

↓

Derived Calendar Projection

↓

Warden

rather than:

Manual Calendar

↓

User Planning

↓

Task List

RealMe should think differently.

It does not need to look unfamiliar to achieve that.
